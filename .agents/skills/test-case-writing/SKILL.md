# Тест-кейсы

Все пути ниже указаны от корня проекта.

1. Найди `ready_artifacts/checklists/check_list_<ID>.md` с отметкой `РЕВЬЮ ПРОЙДЕНО`
   в блоке ревью. Если файла или отметки нет, остановись. Прочитай анализ и
   спецификацию, на которые ссылается чек-лист.
2. Для каждого пункта подготовь кейс с одной проверяемой целью. Объединяй пункты,
   только если у них общие условия и один итог; сохрани ссылки на все пункты.
   Не дублируй одинаковые условия, действия и результаты.
3. Используй структуру ниже. Начальное состояние и подготовку размести в
   предусловиях, проверяемое действие — в шагах. Кейс должен выполняться отдельно,
   без обязательного прохождения другого кейса.
4. Сохрани `drafts/test_cases/<ID>/test_cases_<ID>.md`, сверь покрытие чек-листа через
   `fact-checking`, добавь блок ревью из `AGENTS.md` и передай файл пользователю.

## Формат

- **Название:** действие и проверяемый результат.
- **Приоритет:** высокий/средний/низкий. Если тест-кейс проверяет функционал, падение которого
  может заблокировать дальнейший путь клиента - высокий; если тест-кейс проверяет функционал,
  падение которого пользователь может увидеть, но это не заблокирует дальнейший путь - средний;
  если тест-кейс проверяет функционал, который клиент может не увидеть и функционал не приводит к ошибкам (например
  опечатка в тексте в футере) - низкий.
- **Цель:** что доказывает проверка.
- **Источник:** ссылка на пункт чек-листа и, при необходимости, раздел спецификации.
- **Предусловия теста:** таблица «Шаг / Ожидаемый результат». Для исходного состояния
  ячейка результата может быть пустой; для действия подготовки нужен наблюдаемый результат.
  Одно действие на строку.
- **Тестовые данные:** значения или условия подбора данных, необходимые этому кейсу.
- **Шаги:** таблица «Действие / Ожидаемый результат», одно действие на строку.

Применяй `humanizer-ru` при написании тест-кейсов. Убрать все следы нейросети.
Текст должен быть понятен любому тестировщику, разработчику, аналитику любого уровня.
Избегай сложных конструкций, двусмысленности и академического стиля. При этом оставляй технические термины.
Например: "получить данные ограниченным запросом" поменять на "выполнить запрос".

Называй поля и кнопки так, как в доступных материалах. Вместо «работает корректно»
указывай наблюдаемый результат. Не подставляй реальные идентификаторы и значения
из чужих примеров в новую задачу.

Не копируй название из требований. Формулируй его близко по смыслу к соответствующему
пункту чек-листа.

Если на позитивную проверку можно добавить негативную проверку - ее надо добавлять, если
логика функционала позволяет ее проверить.

Используй техники тест-дизайна: классы эквивалентности, граничные значения как основные.
Если логика функционала позволяет используй технику тест-дизайна: попарное тестирование, состояния и переходов.
Используй перечисленные техники тест-дизайна только к тем тест-кейсам, где по реализации они могут быть применены.

Если необходимо подготовить тестовые данные указывай это. Очевидные шаги предусловия не должны описываться,
например: `определена база данных для выполнения запроса` или `установлено подключение к базе данных`.

[Примеры лида](reference/etalon_test_cases.md) показывают описание шагов. Они не
заменяют эту структуру и не являются требованиями к другим задачам.

## Ограничения

- Нельзя использовать указатели, коды, сокращения. Например: М0 - это состояние
  клиента с действительной картой.
- Нельзя использовать все техники тест-дизайна к тест-кейсу без анализа, насколько
  она применима к выбранному тест-кейсу.
- Если шаги касаются одной формы, совместить их в одном шаге. Например: есть форма для заполнения
  реквизитов карты. У нее 3 поля. Заполнение всех полей должно быть в одном шаге, если это не проверка
  валидации и описана "Заполнить форму реквизитов карты валидными значениями"

---

## Если данных не хватает

Не придумывай статус, текст ошибки, способ подготовки или признак завершения
операции. Укажи пробел рядом с соответствующим кейсом и вопрос в блоке ревью.
Кейс с неизвестным ожидаемым результатом или невоспроизводимым предусловием
остаётся заблокированным, а не готовым к выполнению.

SQL для проверки данных пиши как ограниченный `SELECT` с нужными столбцами и
фильтром по выбранной сущности. Укажи БД и схему из источника; если они неизвестны,
пометь запрос как шаблон. Не выводи бизнес-правила из одного DDL. Самостоятельно
не выполняй SQL и не меняй данные. Не публикуй кейсы в Test IT без отдельной просьбы.
