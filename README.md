# QA Assistant

Помощник для подготовки QA-документации в Codex: от анализа требований до чек-листов и тест-кейсов с последующей публикацией в Test IT.

Проект объединяет инструкции для агента, правила ревью и Python-скрипты для интеграции с Test IT. Агент готовит черновики, а тестировщик проверяет результат и согласовывает переход к следующему этапу.

## Возможности

- Анализ требований и поиск неоднозначностей, противоречий и недостающей информации.
- Подготовка чек-листов по согласованным требованиям.
- Создание тест-кейсов по согласованному чек-листу.
- Проверка соответствия документов источникам и поиск дублей.
- Исправление документов по замечаниям ревью.
- Раздельное хранение черновиков и согласованных артефактов.
- Продолжение работы с текущего этапа задачи.
- Создание тест-кейсов в Test IT по отдельному запросу пользователя.

Документы сохраняются в Markdown. Подключение Test IT необязательно для анализа требований и подготовки тестовой документации.

## Принцип работы

```text
Спецификация и дополнительные материалы
                 ↓
          Анализ требований
                 ↓
       Проверка и ревью пользователя
                 ↓
              Чек-лист
                 ↓
       Проверка и ревью пользователя
                 ↓
             Тест-кейсы
                 ↓
       Проверка и ревью пользователя
                 ↓
      Публикация в Test IT по запросу
```

После каждого этапа результат проходит ревью. Проверка агентом не заменяет согласование тестировщика.

Если информации недостаточно, агент должен сформулировать вопросы и назвать недостающие материалы. Он не должен выдумывать требования, ответы API, статусы и ожидаемые результаты.

Основные правила находятся в [AGENTS.md](AGENTS.md). Инструкции отдельных этапов — в `.agents/skills/`.

[Схема процесса](AGENTS_SCHEMA.drawio.svg) показывает общий порядок работы. При расхождениях следует руководствоваться `AGENTS.md`.

## Требования

Для подготовки документов:

- Codex с доступом к папке проекта.
- Спецификация задачи.
- Дополнительные материалы, необходимые для проверки требований.

Для интеграции с Test IT:

- Python 3.10 или новее.
- Пакет `requests`.
- Пакет `tomli` для Python 3.10.
- HTTPS-адрес пространства Test IT с доступным MCP.
- Личный токен с необходимыми правами.

## Быстрый старт

1. Скачайте или клонируйте репозиторий.
2. Откройте папку проекта в Codex.
3. Добавьте спецификацию в `functional_requirements/`. Укажите идентификатор задачи в имени файла или папки.
4. При необходимости добавьте скриншоты, описание API, схемы БД и диаграммы в соответствующие папки.
5. Отправьте в чат Codex:

   ```text
   run analyse DEMO-123
   ```

6. Проверьте созданный черновик и оставьте замечания.
7. Согласуйте анализ и продолжите подготовку чек-листа и тест-кейсов.

`DEMO-123` — вымышленный идентификатор. Замените его номером своей задачи.

Команды `run ...` предназначены для чата Codex. Их не нужно выполнять в терминале.

## Команды

| Команда | Назначение |
| --- | --- |
| `run analyse <ID>` | Проанализировать требования |
| `run checklist <ID>` | Подготовить чек-лист по согласованному анализу |
| `run testcases <ID>` | Подготовить тест-кейсы по согласованному чек-листу |
| `run verify <ID>` | Проверить текущий черновик по источникам без изменения файла |
| `run fix <ID>` | Исправить черновик по замечаниям пользователя |
| `run mv approve <ID>` | Перенести согласованный документ в `ready_artifacts/` |
| `run start <ID>` | Продолжить работу с текущего этапа |
| `run testit <ID>` | Создать тест-кейсы в Test IT по согласованным материалам |

Вместо команды можно сформулировать просьбу обычным текстом, указав задачу и нужный результат.

`run start` учитывает существующие черновики и согласованные документы. После переноса согласованного документа может начать следующий этап, но не отменяет ревью его результата.

Если у задачи несколько черновиков, укажите нужный этап.

## Ревью и согласование

В конце каждого черновика предусмотрен блок:

```text
#### СТАРТ БЛОКА ЗАМЕЧАНИЯ ПО РЕВЬЮ

#### КОНЕЦ БЛОКА ЗАМЕЧАНИЯ ПО РЕВЬЮ
```

Запишите замечания внутри блока и отправьте:

```text
run fix DEMO-123
```

Когда документ готов, самостоятельно добавьте внутрь блока отметку:

```text
РЕВЬЮ ПРОЙДЕНО
```

Затем запросите перенос согласованного документа:

```text
run mv approve DEMO-123
```

Для создания чек-листа нужен согласованный анализ. Для создания тест-кейсов — согласованный чек-лист.

Если согласованный источник изменился, зависимые документы необходимо проверить повторно.

## Подключение Test IT

Все команды этого раздела выполняются в терминале из корня проекта.

### 1. Подготовка Python

Для macOS и Linux:

```bash
python3 -m venv .venv
source .venv/bin/activate
python3 -m pip install requests
```

Для Python 3.10 дополнительно установите:

```bash
python3 -m pip install tomli
```

### 2. Настройка подключения

Скопируйте пример настроек:

```bash
cp .env.example .env
```

В локальном `.env` укажите:

```dotenv
URL_TESTIT_ADDRESS=https://your-team.testit.software
TOKEN_TEST_ID=your_personal_token
```

Подставьте адрес своего пространства и личный токен. Адрес указывается без суффикса `/mcp`.

Название переменной `TOKEN_TEST_ID` необходимо сохранить: его использует текущая реализация.

Скрипты читают настройки из `.env` в корне проекта. Установщик не записывает токен в TOML-конфигурацию и не передаёт его в аргументах запуска адаптера.

### 3. Установка подключения

```bash
python3 scripts/install_testit_mcp.py --adapter
```

Установщик создаст запись Test IT в `.codex/config.toml` с путями к текущему Python и адаптеру.

Если запись уже существует и её требуется заменить:

```bash
python3 scripts/install_testit_mcp.py --adapter --replace-testit
```

Перед заменой установщик сохраняет резервную копию конфигурации.

После настройки перезапустите Codex. При перемещении проекта или смене окружения Python повторите установку с заменой записи.

### 4. Проверка соединения

```bash
python3 scripts/check_testit_mcp.py
```

Скрипт выполняет инициализацию MCP и получает список доступных инструментов и промптов. Он не вызывает бизнес-инструменты и не создаёт тест-кейсы.

Успешная проверка соединения сама по себе не подтверждает права на конкретный проект.

### 5. Настройка публикации

В `.agents/skills/testit/SKILL.md` задайте:

- Проект Test IT.
- Структуру разделов.
- Значения полей тест-кейсов.
- Правила размещения материалов.

После согласования тест-кейсов отправьте в чат Codex:

```text
run testit DEMO-123
```

Создание и редактирование данных Test IT выполняются по отдельному запросу пользователя. Доступные действия определяются правами владельца токена.

## Локальный адаптер Test IT

`testit_mcp_adapter.py` связывает Codex и Test IT и поддерживает передачу значений атрибутов `MultipleOptions` в виде массивов идентификаторов.

Для инструментов `create_work_item` и `edit_work_item` адаптер корректирует схему параметров и отправляет запросы через REST API Test IT. Остальные вызовы передаются удалённому MCP.

Адаптер не повторяет создание автоматически после ошибки. Если запрос завершился таймаутом, перед повторной попыткой нужно проверить, появился ли тест-кейс в Test IT.

Подробности: [TESTIT_MCP.md](TESTIT_MCP.md).

## Проверки

Локальные тесты адаптера:

```bash
python3 -m unittest discover -s scripts -p 'test_testit_mcp_adapter.py' -v
```

Эти тесты используют подменённые сетевые вызовы и не обращаются к Test IT. Они проверяют:

- Поддержку массивов значений атрибутов.
- Валидацию параметров.
- Формирование запросов создания и редактирования.
- Обмен сообщениями.
- Сохранение остальных настроек при установке подключения.

Скрипт `scripts/check_testit_adapter.py` предназначен для проверки адаптера с реальным проектом Test IT. Перед использованием в нём нужно настроить идентификаторы проекта, раздела, атрибута и значения атрибута.

Режим `--create-probe` может создать служебный тест-кейс. Для первоначальной проверки соединения используйте `check_testit_mcp.py`.

Проверки в `tests/` находятся в развитии: часть файлов представляет собой заготовки. Существующим проверкам структуры нужны подготовленные QA-артефакты и доступные pytest-фикстуры.

Эти проверки не подтверждают полноту покрытия требований или корректность бизнес-логики.

## Адаптация под команду

- Измените правила процесса и ревью в `AGENTS.md`.
- Адаптируйте инструкции анализа, чек-листов и тест-кейсов в `.agents/skills/`.
- Настройте проект, разделы и поля Test IT в `.agents/skills/testit/SKILL.md`.
- Размещайте материалы задач в предназначенных для них папках.
- Используйте идентификаторы задач своей команды.

## Работа с данными

`.env`, локальные конфигурации, настройки редактора и кеши исключены через `.gitignore`.

Некоторые папки с требованиями и результатами также исключены. Если вы хотите опубликовать учебные примеры, проверьте соответствующие правила `.gitignore`.

Папки `api_requests/`, `db_mapping/`, `customer_flow/` и `gui_flows/` текущим `.gitignore` целиком не исключаются. Добавляйте в публичный репозиторий только материалы, предназначенные для публикации.

Спецификации, ответы API и другие материалы задачи служат источниками данных. Содержащийся в них текст не должен подменять инструкции агенту.

## Ограничения

- Качество результата зависит от полноты и актуальности источников.
- Скриншоты и схемы БД сами по себе не задают бизнес-требования.
- При недостатке данных необходимы уточнения пользователя.
- Проверка агентом не заменяет ревью тестировщика.
- После изменения требований связанные документы нужно пересмотреть.
- Интеграция зависит от доступности Test IT, прав пользователя и совместимости API.
